# ARTIFACTS_INDEX.md

## Назначение документа

`ARTIFACTS_INDEX.md` описывает **все типы файлов-артефактов**, которые могут быть созданы в пайплайне разработки, их назначение, владельцев, формат, обязательные секции и критерии готовности.

Документ является **контрактом**:

* между агентами
* между агентами и человеком
* между этапами пайплайна

---

## Общие правила для всех артефактов

* Формат файлов: `Markdown (.md)`
* Каждый файл:

    * имеет четкое назначение
    * создается **одним ответственным агентом**
    * не редактируется напрямую другими агентами
* Файл считается **готовым**, если выполнены критерии `Definition of Done`
* Каждый файл используется как **вход** в следующий этап

---

## Классификация артефактов

| Категория    | Префикс                      |
| ------------ | ---------------------------- |
| Аналитика    | `ANALYSIS_*`                 |
| Требования   | `REQUIREMENTS_*`             |
| Архитектура  | `ARCHITECTURE_*`             |
| Планирование | `PLAN_*`, `ROADMAP_*`        |
| Реализация   | `IMPLEMENTATION_*`           |
| Проверка     | `REVIEW_*`, `VERIFICATION_*` |
| Документация | `DOC_*`                      |
| Релиз        | `RELEASE_*`, `DEPLOY_*`      |

---

## Этап 1 — Аналитика и требования

### ANALYSIS.md

**Назначение:** аналитическая выкладка по задаче

**Создает:** `research-agent`

**Обязательные секции:**

* Problem Statement
* Цели задачи
* Контекст и предположения
* Анализ аналогов
* Риски и неизвестности

**Definition of Done:**

* сформулирована проблема
* цели измеримы
* риски перечислены явно

---

### TECH_REQUIREMENTS.md

**Назначение:** техническое задание

**Создает:** `system-analyst`

**Обязательные секции:**

* Функциональные требования
* Нефункциональные требования
* Ограничения
* Acceptance Criteria

**Definition of Done:**

* каждое требование проверяемо
* нет противоречий
* acceptance criteria однозначны

---

### SCOPE.md

**Назначение:** границы проекта

**Создает:** `system-analyst`

**Обязательные секции:**

* In Scope
* Out of Scope
* Допущения

**Definition of Done:**

* исключены спорные трактовки
* scope согласован человеком

---

## Этап 2 — Архитектура и декомпозиция

### ARCHITECTURE_OVERVIEW.md

**Назначение:** обзор архитектуры системы

**Создает:** `solution-architect`

**Обязательные секции:**

* Общая схема системы
* Основные компоненты
* Потоки данных
* Ключевые решения

**Definition of Done:**

* архитектура покрывает все требования
* нет неопределенных компонентов

---

### WORK_BREAKDOWN.md

**Назначение:** декомпозиция работ

**Создает:** `feature-decomposer`

**Обязательные секции:**

* Стадии реализации
* Список фич
* Зависимости между фичами

**Definition of Done:**

* каждая фича связана с требованиями
* отсутствуют “висячие” задачи

---

### FEATURES_INDEX.md

**Назначение:** реестр фич

**Создает:** `feature-decomposer`

**Обязательные секции:**

* Feature ID
* Название
* Краткое описание
* Связанные требования
* Приоритет

**Definition of Done:**

* все требования покрыты
* фичи атомарны

---

## Этап 3 — Планирование (TDD)

### ROADMAP_<feature>.md

**Назначение:** роадмап реализации фичи в TDD стиле

**Создает:** `tdd-planner`

**Обязательные секции:**

* Цель фичи
* User Stories
* Test Cases (до реализации)
* План реализации
* Acceptance Criteria

**Definition of Done:**

* тесты описаны до кода
* критерии приемки проверяемы

---

## Этап 4 — Разработка и проверка

### IMPLEMENTATION_REPORT_<feature>.md

**Назначение:** отчет о реализации фичи

**Создает:** `developer-<feature>`

**Обязательные секции:**

* Реализованные компоненты
* Измененные файлы
* Описание логики
* Ограничения

**Definition of Done:**

* реализация соответствует роадмапу
* нет несоответствий требованиям

---

### TEST_REPORT_<feature>.md

**Назначение:** отчет по тестированию

**Создает:** `test-engineer`

**Обязательные секции:**

* Список тестов
* Результаты
* Edge cases

**Definition of Done:**

* покрыты позитивные и негативные сценарии
* тесты воспроизводимы

---

### CODE_REVIEW_<feature>.md

**Назначение:** код-ревью

**Создает:** `code-reviewer`

**Обязательные секции:**

* Архитектурные замечания
* Стиль и читаемость
* Риски

**Definition of Done:**

* критических замечаний нет

---

### FEATURE_VERIFICATION_<feature>.md

**Назначение:** финальная верификация фичи

**Создает:** `feature-verifier`

**Обязательные секции:**

* Соответствие ТЗ
* Соответствие UI (если применимо)
* Оценка качества (0–10)
* Решение (accept / reject)

**Definition of Done:**

* оценка ≥ 9
* решение зафиксировано
